# Lowest-latency lossy streaming for the Chromium panel

**Start with adaptive native CDP JPEG for large updates and motion. Keep Efficient lossless for sparse desktop changes.** Native JPEG is already a single encode in Chromium followed by native image decode in the viewing browser. The first experiment should tune that path and remove avoidable waiting for an interactive update. If sustained motion still misses the latency target at acceptable quality, test low-delay H.264 from a raw tab capture source. The right choice depends on which stage dominates at the target link rate and on the text quality the panel must preserve.

## What the checkout does today

| Stage | Implemented path | Latency implication |
| --- | --- | --- |
| Capture | Server-side Chromium produces independent JPEG or PNG images through CDP `Page.startScreencast`. Eya requests one capture in flight and every frame, with capture dimensions bounded and JPEG quality defaulting to 80. It probes Chromium's schema for `sendLastFrame`. | JPEG avoids PNG capture and server-side re-encoding. Latest-frame retention helps preserve a final repaint while credit is held. The fallback stores at most one extra emitted event and can refresh capture after input. |
| Lossless encoding | Rust decodes PNG to canonical RGBA, compares 64×64 tiles, omits unchanged tiles, and selects the smaller raw-DEFLATE replacement or XOR residual for each changed tile. A successful presentation ACK commits the next reference. | Sparse updates can cost hundreds of bytes. PNG capture, full decode and comparison still happen before a frame is omitted. Preparation runs on a blocking worker, and the browser session loop awaits it. |
| Large changes | Tile preparation falls back to the original PNG when changed tiles cover over 60% of the image or the encoded delta reaches the PNG size. Repeated fallbacks can trigger a fresh keyframe after a minimum interval. | Wide scrolls can incur PNG capture and decoding followed by full PNG transmission. A PNG fallback preserves the saved exact reference, including when an empty delta later restores it. |
| Transport | The browser session sends authenticated display chunks of up to 48 KiB through a bounded writer queue. It can process input between chunks. A partially sent frame completes in order, and normal display progress uses one outstanding ACK. | Smaller frames release credit sooner. The writer bound limits application backlog, while queued TCP bytes and retransmissions can still delay fresh display data. An ACK round trip can limit how quickly the next capture arrives. |
| Client | Independent images use browser image decoding and an image swap. Tiles reconstruct offscreen, then commit through `putImageData` and a canvas swap. ACK scheduling includes the panel's FPS interval measured from complete-frame receipt. | A small delta can still require a full-surface client copy. FPS pacing can postpone the next capture, including after an input arrives. The ACK reflects decode/presentation bookkeeping, with physical display timing outside that measurement. |

Source entry points are [server capture and frame dispatch](../eya-server/src/browser_render.rs#L3709), [tile encoder](../eya-server/src/browser_tiles.rs#L73), [transport assembly](../client/browser-transport.js#L367), and [panel presentation](../client/browser-panel.js#L3741). CDP is an image capture interface here. Changing the image format alone does not yield raw compositor pixels or an inter-frame bitstream. [CDP screencast API](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast), [Chromium capture implementation](https://chromium.googlesource.com/chromium/src/+/73d3b8fb794c8c83e33be2ab0df4f131f87088ae/content/browser/devtools/protocol/page_handler.cc)

## What the measurements support

The checked-in production-path experiment used a 1280×720 multilingual text and texture fixture with twelve inputs per mode. It timed dispatch to canvas commit in a harness. The shaped profile capped downstream bandwidth at 5 Mbit/s, added nominal 50 ms RTT, and did not model packet loss. The reported p95 was the largest of twelve samples. The checked-in server renderer, tile codec, client tile decoder and shared inflater match their recorded hashes. The current browser transport differs from the recorded hash, and the harness omits the full panel's FPS pacing. Treat these figures as historical comparisons. [Experiment and methodology](browser-streaming-improvements.md#recorded-production-comparison), [raw results](browser-stream-improvements-results.json)

| Encoding | Mean update payload | Loopback median | Shaped median | Shaped observed p95 |
| --- | ---: | ---: | ---: | ---: |
| JPEG | 282,242 B | 122 ms | 599 ms | 622 ms |
| PNG | 665,524 B | 123 ms | 1,238 ms | 1,300 ms |
| Efficient lossless | 225 B | 91 ms | 163 ms | 188 ms |

The tile bootstrap was 626,222 B and measured separately. In the optimized Rust capture replay, a 222 B caret update took about 5.6 ms to prepare, while an image-animation update took about 15.5 ms and still emitted 365,439 B. Two scroll samples fell back to 337–429 kB PNGs. These timings start at an existing PNG and exclude Chromium capture, transport and presentation. [Optimized Rust measurements](browser-compression-rust-results.json)

At 5 Mbit/s, 282,242 B alone takes about 452 ms to serialize, and a 50 ms payload budget buys roughly 31 kB before framing, retransmission or capacity variation. At 100 Mbit/s, that same JPEG takes roughly 23 ms to serialize. As a first-order comparison, a new encoder that adds 10 ms of combined capture, encode and decode work has to save more than about 6.25 kB at 5 Mbit/s or 125 kB at 100 Mbit/s, assuming identical queues and pacing. Use measured input-to-visible-update latency to decide when those assumptions break.

## Candidate paths

| Candidate | Where it may win | Main cost or risk |
| --- | --- | --- |
| Native CDP JPEG, adaptive quality and resolution | Lowest implementation cost and a strong LAN baseline. Set an explicit frame-byte budget on constrained links, preserve native resolution for text when possible, and compare a lower capture cap for motion. | Still sends the whole image. Quality and resolution reductions can smear small text. Updating CDP settings restarts screencast in the current implementation, so measure the transition and use stable tiers with hysteresis. |
| Exact text tiles plus lossy intra image regions | Mixed screens where a changing photo or video sits next to readable UI. Encode independent JPEG regions from source pixels with native image decode. Try 4:4:4 for colored text and 4:2:0 for photo regions. | PNG capture followed by region re-encoding adds work until a raw source exists. Small regions add headers, decoder calls and possible seams. Exact XOR cannot use lossy pixels as its base. This path needs its own reference and atomic presentation rules. |
| Raw capture plus low-delay H.264 | Sustained motion on a constrained link. Inter-frame prediction can reuse unchanged screen areas and encode displaced content more effectively than independent full images. | Raw tab capture is the first feasibility gate. PNG-to-H.264 adds a PNG round trip, and JPEG-to-H.264 adds generation loss. Actual hardware availability, color conversion and frame copies can determine whether video wins. Secure-context WebCodecs support and the exact decoder configuration must be probed on the viewing browser. |

For a hybrid prototype, test keeping an exact base and compositing lossy image patches as a separate layer. Each displayed update should have explicit replacement or clearing semantics so stale patches never hide updated text. Reset both layers on a tab switch or resize. For scrolling-heavy documents, also test exact, pixel-verified scroll-copy plus an exposed strip as a comparison. It could accomplish the bandwidth reduction at native text quality. SIMD JPEG with selectable chroma subsampling is a practical region encoder; choose based on encode time and legibility. [libjpeg-turbo API](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/src/turbojpeg.h), [SIMD coverage](https://github.com/libjpeg-turbo/libjpeg-turbo/blob/main/simd/README.md)

For video, begin with a persistent encoder, no B-frames or lookahead, bounded rate-control buffering, and explicit recovery keyframes on discontinuities. Compare a software low-delay x264 configuration against hardware encoding where available. Probe WebCodecs with `VideoDecoder.isConfigSupported` and request `optimizeForLatency`; this is a hint and its output delay still needs measurement. Use a bounded decode queue and release every output frame. Drop stale raw work before encode. If an encoded reference is skipped, restart from a decodable keyframe or use a dependency structure that explicitly tolerates the skip. Measure first-keyframe bytes and recovery latency separately. Test VP8 or AV1 later if the H.264 profile fails compatibility or a measured encoder alternative offers a better latency/quality tradeoff. [FFmpeg codec configuration](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb), [WebCodecs decoder configuration](https://www.w3.org/TR/webcodecs/#video-decoder-config)

## Prototype order and decision gates

1. **Instrument the current panel.** Use a deterministic input-triggered color marker for the first correct visible frame. Collect browser-side input-to-visible-update timing, server-side CDP event arrival and prep timings, writer queue age, first/last chunk, client assembly and decoder time, commit, and ACK turnaround. Use per-host monotonic durations and correlate by input and frame sequence. Report commit and a paint proxy separately. An external high-speed recording is needed for physical input-to-photon.
2. **Establish the JPEG Pareto curve.** Compare JPEG80, JPEG65 and JPEG50 at native and bounded capture resolutions against PNG and Efficient lossless. Use fixed tiers first to isolate codec cost. In the full panel, compare the existing ACK pacing with prompt ACK on recent input and separately bounded capture pacing. Then test a single replaceable unsent frame slot with bounded capture credit for independent frames. Keep finish-in-order for a frame already on the wire. Verify the final repaint arrives under both Chromium credit behaviors and that prompt ACK does not recreate a queue of stale frames.
3. **Prototype raw tab capture if motion misses the target.** Evaluate whether the deployed Chromium/headless setup can deliver tab-scoped raw or video frames without capture prompts, whole-desktop exposure, or changes to sandbox or egress boundaries. Measure acquisition, copies, conversion and keyframe latency before writing a new transport. Start over the existing ordered connection to isolate codec results. If retransmission and ordered queues dominate after byte reduction, evaluate a separate authenticated media path with deadline-aware delivery. WebTransport datagrams would additionally require congestion-aware rate control, bounded fragmentation/reassembly and dependency recovery. [WebTransport specification](https://www.w3.org/TR/webtransport/)
4. **Test against interaction and quality targets.** Use idle caret, typing, selection, mixed text/video, scrolling, moving texture, navigation, resize and tab switch. Run loopback, the existing 5 Mbit/s profile, a faster LAN/WAN profile and a shaped link with packet loss and jitter. Use repeated warmed runs with hundreds of inputs per important cell. Measure p50/p95/p99 marker latency, frame age, frame skips, keyframe recovery, wire bytes, CPU, memory and decoder queue depth, including on a low-power client. Compare small-text crops and colored edges at native scale alongside motion quality; aggregate image metrics alone can hide unreadable labels.

A proposed promotion gate is at least 20% lower p95 than the best current mode for the intended workload and link, with readable small text at the agreed quality floor and reliable final-frame delivery after a burst. Treat this as a working benchmark target. A bandwidth win with slower interaction can still serve a bandwidth-saving mode. A lossy mode earns the latency label only when the full panel shows the gain.

Any new wire format needs explicit offered-only negotiation, a JPEG fallback, unchanged meanings for existing image/tile ACKs, and fresh state after resize, mode change, tab switch or reconnect. Preserve existing Noise authentication, bounded allocations and queues, and the permanent update-v1 contract. Roll out behind an opt-in while validating old peers and unsupported decoder configurations.

This report uses source inspection and recorded measurements. It does not claim a measured win for adaptive JPEG, hybrid patches, or H.264 in the current checkout.

## How to make the stream adaptive

The current pipeline adapts **lossless representation and frame freshness**. It chooses replacement versus XOR per changed tile, falls back to PNG for expensive deltas, periodically rebases, and can suspend tiles after repeated failures. It also retains recent frames while waiting for credit. **It has no controller for bitrate, JPEG quality, capture resolution, FPS, or switching between JPEG and Efficient lossless based on observed conditions.** Those settings come from the selected preset. JPEG used during initial tile negotiation is a compatibility fallback. [Panel settings and resize request](../client/browser-panel.js#L3859), [tile encoding decisions](../eya-server/src/browser_tiles.rs#L75), [server ACK handling](../eya-server/src/browser_render.rs#L2488)

### First controller for native JPEG

Put the controller in the Rust browser session, where it can combine capture stats, writer pressure, and matching ACKs. Keep the user's settings as limits and expose the applied tier independently. A first prototype can hold capture resolution and FPS fixed and tune JPEG quality alone.

| Signal | How to use it |
| --- | --- |
| Encoded bytes and capture arrival rate | Keep short histories per tier. A large frame is evidence of cost. Repeated large frames and regular arrivals distinguish sustained motion from a single navigation or scroll burst. |
| Writer queue wait and ACK turnaround | Measure first display enqueue through matching ACK, plus how long the writer takes to accept chunks. Full-frame turnaround includes transfer, decode, pacing, return-path delay and contention. Treat it as an interaction pressure signal. |
| Client first-to-last chunk and receipt-to-commit | Add later as bounded, sequence-correlated feedback if attribution is poor. Receipt-to-commit isolates client decode and rendering. First-to-last chunk is a delivery-rate sample primarily for sufficiently large, continuously transmitted frames. One-chunk frames and idle gaps are poor samples. |
| Recent input and final repaint | Favor getting the next correct update out promptly. After a burst, verify the final repaint or schedule one bounded refresh where Chromium lacks latest-frame retention. Keep codec adaptation separate from ACK pacing in the experiment. |

Do not derive downstream throughput from the client's WebSocket `bufferedAmount`, which describes its outbound queue. The server's last-chunk queue time likewise cannot establish when the bytes left the kernel. Start with observed frame turnaround and writer wait. If using delivery feedback, smooth samples over a short window, ignore samples around reconnects and tier changes, and avoid learning that a link has spare capacity merely because the page was idle.

For an initial controller, try JPEG80 → 65 → 50. Choose a lower tier when several active updates in a row exceed the latency budget and show transfer pressure. For example, use three of the last four frames as an initial threshold. Use a longer clean window before stepping up, a minimum interval between switches, and a one-step upshift probe. These thresholds are experiment inputs. Keep a rolling byte budget as a second check when delivery rate is measurable. At 5 Mbit/s a 50 ms transfer allowance is roughly 31 kB, and the estimated budget should shrink when capacity or latency headroom falls. During idle, keep the last tier until fresh activity supplies evidence. If decode time dominates at the JPEG quality floor, test lowering the capture dimensions. Lower capture rate when sustained production still outruns delivery, while prioritizing a fresh frame after input.

### Switch safely and distinguish scene changes from link changes

Today a JPEG quality or capture-cap change calls `Page.stopScreencast` and `Page.startScreencast`. Reuse that path only at a drained frame boundary. Invalidate pre-restart deferred work and ignore stale events and ACKs from earlier generations. In particular, checking the JPEG signature cannot distinguish a frame from before a JPEG-to-JPEG restart. Validate CDP event ordering on the deployed build before using a restart as a generation boundary. If switch-to-first-frame delay consumes the gain, use longer-lived tiers or prioritize a capture path with live encoder controls. Keep the page's logical viewport fixed when only the capture cap changes. [Current screencast restart and viewport paths](../eya-server/src/browser_render.rs#L7086)

A separate, optional scene policy can prefer tiles during sparse interaction and JPEG during sustained large changes. In tile mode, use the existing changed-area and fallback signals to detect sustained large updates. A single expensive update can be a scroll, resize or navigation. In JPEG mode there is no exact RGBA comparison available for free. Test a bounded low-resolution motion sample or a deliberate PNG probe after activity settles. Compare the cost of returning to tiles, including the bootstrap keyframe, against the expected savings over subsequent updates. Keep the exact reference isolated from JPEG pixels and require a newly presented independent tile reference on return.

Benchmark fixed JPEG, adaptive JPEG and scene switching separately on the same traces. Include bandwidth steps in both directions, healthy-link motion, a slow decoder on a healthy link, an idle-to-input transition, and a short scroll followed by typing. Record how long the controller takes to settle, time lost to restarts, quality-floor violations, and p95/p99 time to the first correct post-input frame. A bitrate change alone does not establish a latency improvement.
