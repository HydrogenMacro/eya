# Embedded browser API compatibility roadmap

This catalog covers browser capabilities as presented through Eya's Browser panel. The Full browser runs a real headless Chromium page on the server and returns rendered frames through `client/browser-panel.js` and `client/browser-transport.js`. Page JavaScript therefore gets Chromium's ordinary DOM and Web APIs where the server environment supports them. The work below concerns the boundary between that page and the client UI, native device capabilities, and the separate Proxy and Local HTML modes. It does not propose reimplementing all of Chromium in JavaScript.

## Implemented first pass

Full browser now reliably forwards JavaScript dialog events, offers one file picker for device and server files, exposes device/server download destinations, provides basic context actions, and confirms `window.print()` before generating a bounded PDF. See [browser.md](browser.md#native-browser-interactions) for limits and wire behavior. Server files currently round-trip through the client; direct server staging, directory selection, rich clipboard and persistent filesystem handles remain future work. Payment, identity, notifications, push and media-device bridges are outside the current implementation scope.

## Implemented second pass

Text/link Web Share, plain-text Clipboard API reads/writes, and clicked `mailto:`/`tel:` links now have bounded, gesture-driven client prompts. Grants are per request; pending actions expire and are cancelled when the tab, session or document changes. Native share offers a copy destination when the client has no share sheet. File sharing, rich clipboard, arbitrary protocols and scripted app navigation remain unsupported.

## Existing support to preserve and improve

| Capability | Current behavior | Work to add |
| --- | --- | --- |
| JavaScript `alert()`, `confirm()`, `prompt()`, and `beforeunload` | Full browser reliably sends CDP dialog control events to the client and waits for a panel dialog response. | Verify and improve on narrow screens, tab switches, navigation races, repeated dialogs, long text, and client disconnect. Ensure every abandoned dialog is resolved or cancelled so a page cannot remain indefinitely blocked. |
| `<input type=file>` and file-input `showPicker()` chooser events | A page chooser opens a combined device/server picker with mixed-source multi-selection, accept hints, cancellation, progress, and bounded transfers. | Improve MIME filtering for server selections and add directory selection where supported. Keep server files server-side where possible; validate paths, file types, byte limits, and chooser lifetime on the server. |
| Page downloads and download shelf | Full-browser downloads are intercepted, streamed to the client, and exposed in Downloads with device and server save destinations. Proxy-mode downloads are separately materialized by the client. | Server saves refuse overwrite and retain the downloaded blob after failure for retry. Improve destination browsing and direct server saves without a client round trip. Keep the current bounded transfer and cleanup behavior. |
| Popups and `window.open()` | Chromium page targets are adopted into Eya tabs; popup targets and closure events are tracked. | Cover blocked popups, named-target reuse, `noopener`/`noreferrer`, user-gesture rules, target ordering/focus, popup close, and opener relationships. Give users a policy for popup creation and a way to open a link in a new Eya tab. |
| Clipboard and text input | Keyboard and composed text are forwarded; paste inserts client plain text. Ctrl/Cmd+C and X copy/cut a bounded plain-text selection to the client clipboard. | Improve rich-text and image copy/paste, selection across frames and editable controls, cut behavior, platform shortcuts, permission/error feedback, and browser-native context-menu actions. Keep clipboard transfer explicit and gesture-driven; do not silently synchronize clipboard contents. |
| Pointer, wheel, touch, and viewport | Mouse, touch, and wheel input are mapped to the displayed remote frame; viewport changes track panel dimensions and DPR. | Improve multi-touch fidelity, pointer capture/cancel, hover and auxiliary buttons, double/triple click counts, stylus/pressure, and accessibility input. Confirm browser zoom and OS display changes retain accurate coordinates. |
| Page navigation and history | Address bar navigation and Back/Forward/Reload operate on the active server tab. | Add per-tab history visibility and recovery for redirects, downloads, same-document navigation, and popups. Preserve focus and scroll state where Chromium exposes it. |
| Client-side proxy runtime | The separate experimental **Proxy browser** panel rewrites or relays some `fetch`, XHR, EventSource, WebSocket, worker, form, and SPA navigation paths. It continuously discloses that some requests may use the client network. | Follow the [proxy roadmap](browser-proxy-roadmap.md): establish an enforceable egress architecture before claiming confinement, and enumerate CORS, credentials, redirects, streaming, abort, cache, and origin semantics. Keep unsupported cases explicit. |
| Local HTML viewer | Relative document/assets and links are resolved through the authenticated file callback; scripts are disabled. | Improve file chooser and download behavior only if it can preserve the viewer's script-free boundary. Keep script execution, network access, and form submission disabled unless a separate security design authorizes them. |

## Missing client-mediated browser capabilities

These APIs require an explicit bridge or user interface because a headless server page cannot directly invoke a capability on the user's phone or computer. A returned `navigator.*` object alone is not evidence that the capability is usable.

| API or behavior | Current gap | Reasonable implementation |
| --- | --- | --- |
| `window.print()` / `window.print` | Full browser confirms page print requests and generates a bounded PDF in Downloads, also available from the options menu and Ctrl/Cmd+P. | Add print layout options and preview; current output includes backgrounds and honors CSS paper size. Preserve cancellation and output limits. Do not print through the Eya server's physical printer by default. |
| `navigator.share()` / `navigator.canShare()` | Text/link sharing opens a client share/copy prompt; page promises reflect completion or cancellation. | Consider bounded file sharing only if needed. Improve platform feature reporting and preserve the existing gesture, cancellation and origin checks. |
| `navigator.clipboard.read*()` and rich clipboard formats | Plain-text readText/writeText calls are bridged with per-request client approval, alongside copy, cut and paste. | Add permission-aware, gesture-bound reads and writes for supported formats; retain plain-text fallback. Never expose clipboard reads to background page code. |
| File System Access API (`showOpenFilePicker`, `showSaveFilePicker`, `showDirectoryPicker`) | Open picker activity can surface through Chromium chooser handling, but it is not an Eya file picker workflow; save/directory semantics are not bridged to client or server storage. | Implement picker handles as scoped capabilities. Let users choose client upload, Eya server files, client download, or server save. Preserve handle lifetime and permission semantics or clearly report unsupported persistence. Do not translate page-selected paths into unrestricted server paths. |
| Drag-and-drop from client to page | The server page cannot receive native client `DataTransfer` files through the rendered image. | Add a client overlay drop target and bounded upload transfer that populates the page's drop event with virtual `File` objects. Preserve file names/types and cancellation; document that OS paths are never exposed. |
| `navigator.geolocation` | No client location permission or position bridge. Server location would be wrong for the user. | Add opt-in client geolocation with a clear per-origin permission prompt, bounded accuracy/update rate, denial/timeout mapping, and revocation. Default to denied. |
| `navigator.mediaDevices.getUserMedia()` and device enumeration | Server Chromium has no access to the client's camera/microphone. | If needed, bridge selected client audio/video streams over a dedicated, encrypted, bounded media channel with explicit device permission and lifecycle controls. Otherwise deny clearly; never silently use server devices. |
| `getDisplayMedia()` / screen capture | No client screen picker or stream bridge. | Add only with an OS-mediated client screen-selection prompt and a separate bounded media transport; stop tracks on tab/session close and expose capture state. Otherwise deny. |
| `navigator.permissions.query()` | Permission state is not a coherent view of client permissions and server Chromium permissions. | Define a permission registry that reports `granted`, `prompt`, or `denied` consistently with each implemented bridge. Return denied/unsupported for capabilities not provided. |
| `Notification` and Push API | No client notification permission UI or delivery bridge. Service worker push also has no Eya push service. | Add opt-in notifications through the client OS with per-origin permission, bounded title/body/icon/action data, click routing, and revocation. Push requires a separate subscription and delivery service; do not imply support without one. |
| Web Share Target, payment, credential, identity, and authentication APIs (`PaymentRequest`, WebAuthn, Credential Management, FedCM) | No client authenticator, payment sheet, identity provider, or credential-store bridge is specified. | Deny cleanly until a dedicated native prompt and end-to-end protocol exist. Never forward secrets to logs or unrelated page/session state. Payment and identity bridges need explicit product and security designs first. |
| External protocols and app handoff (`mailto:`, `tel:`, custom schemes, `registerProtocolHandler`) | Clicked mailto: and tel: links prompt before client app handoff. | Consider scripted mailto:/tel: navigation and additional explicitly allowed schemes only if needed. Validate schemes and payloads; never invoke arbitrary custom schemes automatically. |
| Native fullscreen, orientation, pointer lock, and vibration | The page can request browser APIs, but the panel does not provide a consistent client-native permission or state bridge for device fullscreen/orientation/haptics. | Map fullscreen to the panel's own fullscreen control and report state. Add orientation or haptics only through explicit client APIs and permission/state feedback; otherwise return a clear unsupported result. |
| Browser context menus and selection actions | Full browser offers copy/cut/paste and web-link open/copy actions, and respects page context-menu cancellation. | Extend context actions across frames and shadow roots, and add image/download actions. Bridge only a bounded menu model from the active page and preserve normal page context-menu events. |

## Cross-cutting requirements

- Keep Full browser, Proxy, and Local HTML behavior distinct. Full browser is real Chromium with server-side networking; Proxy is a compatibility shim; Local HTML intentionally disables scripts.
- For a native capability, define its activation gesture, permission prompt, result/error mapping, lifecycle, cancellation, and behavior when the client disconnects before adding an API shim.
- Scope prompts and grants to an origin and tab where practical. Make revocation visible. Default device, clipboard-read, notification, location, screen, payment, and identity access to denied until the user grants it.
- Bound bytes, concurrent requests, timeouts, and retained objects on both client and server. Treat every client-supplied name, MIME type, path, URL, and permission response as untrusted.
- Keep page APIs honest: unsupported APIs should fail using the expected browser error shape rather than return success with inert data.
- Add compatibility coverage to the narrow browser panel, transport, or server integration suite for each API bridge. Exercise grant, deny, cancel, disconnect, tab-close, and resource-limit paths.

## Implementation order

1. Improve file chooser integration with the existing server file browser and save destinations for downloads; these build on current authenticated file and transfer mechanisms.
2. Complete dialogs, clipboard, popup, and context-menu behavior, which are direct browser-panel interactions.
3. Add opt-in client share and print/PDF workflows.
4. Consider geolocation, notifications, and media bridges only when there is a clear product need and a dedicated permission/lifecycle design.
5. Keep payment, identity, authenticator, and push services out of scope until their external trust and service requirements are defined.
