# Releases, client updates, and wire compatibility

Eya uses SemVer, starting with **1.0.0**. `VERSION` is the release-train version; `client/version.js`, the Cargo package version and its lockfile entry must agree. `node client/build.mjs` rejects mismatched versions. Client and server release numbers describe software releases, not wire encodings. A different client/server version is expected and is not grounds to reject authentication or a connection.

## Updating a client

A top-right download indicator appears when the server offers a newer client. Clicking it opens the File System Access save picker immediately where supported (including hosted clients); otherwise it downloads a replacement. Canceling the picker leaves the indicator available to retry. Checks start automatically when a configured client opens, without requiring a workspace connection.

Navbar menu → Client updates shows the running client and checked server versions. A connection attempt checks automatically, independently of whether the workspace protocol succeeds. While server credentials are configured, checks run at most once per hour per server/password; Check for updates bypasses that interval. Failed checks never end terminals or change workspace state. Updates are offered only for a higher SemVer precedence, including prereleases; build metadata alone is not an update and an older server never causes an automatic downgrade. Upgrade the server binary to publish a new embedded client.

The download uses the configured server's independently Noise-authenticated `/ws/update` channel, including from file and data origins. There is no third-party update service, password-bearing URL, cross-origin HTTP fetch, shell, filesystem service, or PTY creation. The client verifies bounded artifact length, exact chunk offsets/lengths and SHA-256 before saving anything. The digest detects corruption and pins a release; authentication comes from Noise and the shared password. Updates trust the same server that already has terminal authority. The server sends its unconfigured template; credentials are inserted locally and never requested in an update payload.

- HTML clients download a self-contained HTML replacement. SVG clients download a self-contained SVG replacement. Compressed clients receive the corresponding uncompressed format.
- Where the browser supports a file-save picker, **Save update to file…** lets you select and overwrite the existing client file. The browser controls the file permission and overwrite confirmation. The verified artifact is written through the file API's replacement stream. Other browsers download a replacement with the standard client filename; use the browser/file manager's replace action. A browser cannot silently overwrite the file from which it was opened.
- Hosted clients can reload the server's latest embedded version, with confirmation to save edits and the workspace first. Download also creates a configured standalone copy.
- A data URL cannot replace its own URL/bookmark in place. The update UI explains this and downloads an HTML file to open instead where the browser permits server access from data origins. Browsers that block that access show a recovery message and **Open server client** opens the configured server's current hosted HTML client in a new tab, without putting the password in the URL. That hosted client uses server defaults; custom embedded settings remain in the old data URL.

Downloads preserve the complete original embedded configuration, including unknown fields, custom font, startup panel, compression choice and command, and use the currently entered server URL/password. JSON is script-escaped before embedding. A hosted download becomes standalone (`hosted:false`). Settings stored in a saved server workspace return when that workspace is explicitly selected. Anonymous workspaces, dirty editors, unsent input and renderer state remain in the old page; an update never reloads or replaces it automatically. Save edits and save/select a named workspace before changing pages. Opening the new client must never implicitly rerun commands or recreate an unavailable session.

## Permanent recovery bootstrap v1

**Every future server release, including major releases, must retain `/ws/update`, its Noise suite, `eya-update-v1` prologue, password derivation, and this contract. Every future client must retain a working bootstrap-v1 updater.** This is the escape path when application protocols or wire optimizations change. From the first update-capable release onward, a client can download the current release directly, without installing intervening releases, negotiating the workspace protocol, migrating local storage, or executing downloaded code in the old page. Clients predating this feature need one manual replacement.

Reverse proxies must forward `/ws/update` with WebSocket upgrades alongside `/ws`; prefix-mounted clients derive `.../ws/update` from `.../ws`. Preserve that mapping across infrastructure changes. An old server without this endpoint reports an unavailable service; it continues serving the existing application connections.

The endpoint uses `Noise_NNpsk0_25519_ChaChaPoly_BLAKE2b`, with prologue bytes `eya-update-v1`. Derive the PSK exactly as for existing Eya connections: decode a 64-hex-character secret to 32 bytes, otherwise SHA-256 its UTF-8 bytes. Each WebSocket starts a fresh handshake and cipher nonces. Binary WebSocket messages contain one Noise message (maximum 65,535 bytes). The responder handshake has an empty payload; no artifact/manifest is sent until an encrypted request authenticates the initiator. No application confirmation prefix or frame-type byte is used here.

Decrypted requests/responses are UTF-8 JSON objects. Requests have `v:1`, `id` (unsigned 32-bit integer) and `op`. Unknown object members are ignored. Send one request at a time. A response echoes `id` and has `ok:true` or `ok:false,error:{code}`. Unknown operations return `unsupported_operation`; malformed versions/IDs return `invalid_request`. No error enables a fallback to unauthenticated HTTP.

| Operation | Request members | Success response members |
| --- | --- | --- |
| `manifest` | none | `v:1`, `client`/`server` SemVer strings, `sha256` lowercase hex, `bytes`, `chunk:32768`, `artifact:"html-template-v1"`, `config:"eya-config-v1"` |
| `read` | `sha256`, `offset` (byte offset, 0 ≤ offset < bytes) | `v:1`, `offset`, `data` (standard base64 for the next min(32768, remaining bytes) bytes) |

`release_changed` means the pinned digest is unavailable; check again before retrying. `invalid_offset` rejects offsets outside the artifact. Unknown response members remain skippable. Byte offsets can split UTF-8 code points; decode only after reassembly. The client accepts templates up to 32 MiB and authenticates/hashes every chunk before packaging. Keep the bootstrap-v1 artifact within that bound forever, even if future releases need a separate larger distribution. Preserve its exact single `<script id="eya-config" type="application/json">{}</script>` insertion marker and self-contained classic-script HTML structure. SVG packaging removes executable HTML script elements and executes their bodies as SVG scripts after installing the XHTML DOM prelude. Preserve compatibility with that packaging in bootstrap-v1 templates. Configuration schema v1 is additive: keep the meaning and units of existing fields, preserve unknown fields, and supply safe defaults for absent fields. A future incompatible config/artifact format needs an additional endpoint/format while this one remains usable.

Server bounds: four separate update slots (never consuming terminal/session slots), 10-second handshake/send deadlines, 30-second per-request idle deadline, ten-minute connection lifetime, 4096-byte plaintext requests, and at most one 32 KiB artifact chunk per response. The client uses 12-second handshake and 15-second request deadlines, bounds all allocations, and closes channels after checks/downloads or errors. A failed/canceled update leaves the running page intact and never opens a file writer before integrity validation.

## Release standards

- PATCH fixes compatible behavior/security defects; MINOR adds optional behavior with old defaults; MAJOR may change application APIs or UX, but never removes the permanent updater or silently reinterprets a deployed wire field. SemVer's major-release allowance does not override the recovery promise.
- Servers support deployed baseline terminal protocols v1–v4 and workspace v1 with their original framing and semantics. Old clients keep working with new servers. New clients tolerate missing optional fields/capability selections and use raw baseline formats with old servers; features requiring an unavailable workspace/browser API must fail explicitly without spawning a replacement session or replaying mutations. Version equality is never a feature test.
- Roll out a new server before clients that require its optional feature. Keep old decoders/handlers when introducing new encodings; a major release adds a new explicitly negotiated protocol instead of reusing an old identifier. Retiring a deployment-specific feature requires an explicit operator migration and continued updater availability. Never silently downgrade an operation with different security/identity semantics.
- Server restarts terminate in-memory PTYs/browser runtimes. Saved workspace definitions persist; live processes need a host process manager for restart survival. Client updates alone leave the current page and server processes running. New clients open a fresh Anonymous workspace and require explicit selection/takeover of retained sessions. Pending file/system/Docker mutations are not automatically replayed across an update/reconnect.
- Authentication prologues, host identity, logical paths, authorization, quotas, timeouts and decoded-size bounds are part of the protocol contract. Do not negotiate a security boundary away. Keep secrets out of logs, URLs and child-process environments.

## Extensible application wire

Existing binary frame tags and their exact payloads are immutable. Terminal compression remains the deployed opt-in `compression:"deflate-raw"` offer/ready selection, with decoded offsets, independent blocks and the existing 8 KiB bound. A missing selection means raw. Never send compressed frames to an unnegotiated peer. Browser protocols retain their distinct Noise prologues; the same additive JSON/explicit selection rules apply to future browser extensions.

Workspace-v1 and terminal-v4 confirmations can now include `capabilities:["extensions-v1"]`. The server selects only offered, implemented capabilities in `ready.capabilities`; absent means `[]`. Unknown offers are ignored and no new frame is sent to an old peer. `ready.versions` reports software versions and supported protocol families for diagnostics. Existing peers ignore these added fields. Capabilities are attachment-local and renegotiated after every fresh Noise handshake, including resume.

With `extensions-v1` selected, frame **12** contains one UTF-8 JSON envelope: `v:1`, `kind` (`request`, `response`, `event`), namespaced `op` (1–128 UTF-8 bytes), optional `required` boolean, and extension-specific data. Requests/responses carry an `id` unsigned 32-bit correlation ID. Responses carry `ok` and either `data` or `error:{code}`. Unknown members are ignored; unknown optional events are ignored; unknown requests receive a correlated `unsupported_operation` error. Unknown required events, malformed envelopes, unknown envelope versions and unnegotiated frame types fail the attachment rather than being interpreted as terminal/file bytes. Servers currently originate no requests/events; clients issue none, so unsolicited responses are invalid. A future mandatory operation or server-originated request requires its own additional capability; selecting the generic envelope alone never proves support for a particular operation. `protocol.info` is a read-only implemented request returning protocol families and release versions. The existing encrypted frame size limit bounds the entire envelope.

Workspace-v1 additionally offers `server-config-v1` for authenticated process-local admission settings. It is selected only when both `extensions-v1` and `server-config-v1` are offered; the generic extension capability alone does not authorize these operations. Settings use the existing frame-4 JSON service request encoding and return a clear unsupported-feature result without that selection. See [system-panels.md](system-panels.md#live-server-limits) for fields, bounds, revision checks and non-disruptive quota changes.

Future optimizations (binary metadata, compression, dictionaries, batching, alternate integer formats) need their own immutable capability/version identifiers, explicit offer/selection, limits for encoded **and decoded** sizes, byte order/offset units, independent framing and reset semantics, and a baseline fallback. A JSON envelope may negotiate or describe such a feature but must never switch a stream's encoding implicitly. Define ordering, ACK/replay accounting, reconnect reset and mutation idempotency before shipping. Never silently drop terminal output or reinterpret unsupported bytes. Unknown optional notifications are skippable only inside this negotiated envelope; making all unknown binary tags skippable would hide corrupt offsets and mandatory operations.

Release gate: rebuild client before Rust, run Cargo fmt/check/test, the update browser/protocol suite, terminal compatibility/reconnect tests, and generator artifact tests. Cover old→new, new→old/missing fields, unknown offers/operations/events, authentication failure, bounded/corrupt/interrupted downloads, SVG/XML packaging, config preservation and save cancellation. Changes to the bootstrap must retain the frozen v1 fixtures and direct-leap update tests. Tests: `NODE_PATH=client/node_modules node tests/client-updates.cjs` and `NODE_PATH=client/node_modules node tests/wire-compatibility.cjs`.
