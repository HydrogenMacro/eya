# Browser panel

The Browser panel provides an address bar, Back, Forward, Reload, and a tab menu. **Proxy browser** is a separate experimental panel available from New panel; it renders pages on the client and contains Local HTML viewing. Open the tab menu to switch or close a tab, or create a tab with the button at its bottom. The tab button shows the open tab count. On mobile, tap Activate keyboard in the accessory bar to open the keyboard for the page; tapping the page alone does not open it. The options menu contains page zoom and fullscreen controls. The remote viewport follows the panel content size multiplied by the client window’s device pixel ratio (DPR); page zoom divides that size. Panel resizing, browser zoom, and display DPR changes update the viewport automatically. The viewport scales down proportionally to fit the 8192×8192 server limit, with a minimum of 320×240. Mouse, touch, and wheel input use the dimensions and letterboxing of the displayed frame, including while a resize is pending. Remote page keyboard input is forwarded when the page has focus, subject to shortcuts reserved by the client browser or operating system. Paste and composed text use the client's text input and clipboard events. Ctrl/Cmd+C and Ctrl/Cmd+X copy or cut the remote selection to the client clipboard as plain text (up to 12 KiB of JSON-encoded text); native copy/cut events use the same path. Copy/cut requires a secure client context and clipboard permission. Password fields are excluded, and cut deletes the still-matching selection only after the clipboard write succeeds. Clipboard sharing is gesture-driven; rich text, images, and automatic background clipboard synchronization are not supported.


### Native browser interactions

Full browser presents `alert`, `confirm`, `prompt`, and `beforeunload` in client dialogs. Dialog events use the reliable control-event queue so console/network traffic cannot drop them.

File inputs open a client picker with **Add from device** and **Browse server files**. Multi-file inputs can combine both sources in one selection. Selections are capped at eight files, 16 MiB per file and 32 MiB total; single-file inputs replace the previous selection. The device chooser receives the input's `accept` hint, also shown in the picker. Server selections use Eya's authenticated file APIs, with size checks before reading, and are then transferred into Chromium's private upload directory. They currently round-trip through the client. Directory uploads and persistent File System Access handles are not implemented. Cancelling or changing tabs invalidates the picker; transfer progress and failures appear in it.

**Browser options → Downloads** opens the download pane. Completed downloads can be saved to the device or to a new server file path. Server saves use the existing authenticated atomic upload operation and refuse to overwrite existing files; choose another path after a conflict. Download transfer remains bounded at 64 MiB and two concurrent downloads.

`window.print()`, Ctrl/Cmd+P, and **Browser options → Print / PDF** open a confirmation prompt. Confirming creates a PDF in Downloads with print backgrounds and the page's CSS paper size, using Chromium's [printToPDF streaming API](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-printToPDF). Output is capped at 64 MiB, streamed in bounded chunks, and temporary files and CDP handles are removed after completion or failure. Cancelling the prompt produces no PDF. The server does not send output to a physical printer. `window.print()` returns immediately after requesting the client prompt; print layout options and synchronous print-dialog blocking are not emulated. Browser transport opcode 36 requests PDF generation for the active tab; `print-request` status events notify the client of page requests, and the existing download frames carry the PDF.

`navigator.share({title, text, url})` and `navigator.canShare()` support text and HTTP/HTTPS links. A client prompt offers the device share sheet when available and **Copy instead** as a share destination. Relative URLs resolve against the remote page. File sharing is unsupported and `canShare` rejects file payloads. Native share cancellation rejects the page promise with `AbortError`. See the [Web Share specification](https://www.w3.org/TR/web-share/) for the underlying API.

`navigator.clipboard.readText()` and `writeText()` now bridge plain text to the client clipboard. Reads require **Allow once**; writes preview the requested text before **Copy**. No lasting clipboard grant is stored. Client browser clipboard permissions still apply, and text is capped at 12 KiB after JSON encoding. Rich clipboard `read()`/`write()` and clipboard permission-query synchronization remain unimplemented.

Clicked `mailto:` and `tel:` links ask before opening an app on the client device. Other custom protocols, scripted location changes and `registerProtocolHandler` are not bridged. App links are capped at 4096 bytes and never executed by the server.

These actions require a gesture in the active top-level remote page (a forwarded pointer, touch or key press within five seconds); clipboard/share additionally require a secure remote origin. Existing Permissions Policy restrictions are honored when Chromium recognizes the relevant feature. Prompts show the requesting origin and are tied to the tab and execution context. The server checks Chromium execution-context metadata for the origin and top-level frame, rather than trusting origin labels from page scripts. Tab changes, disconnects, takeover and timeout cancel pending actions; navigation invalidates the requesting context. One native action can be pending per browser session. Requests are capped at 16 KiB and expire after 55 seconds on the server (60 seconds in the page). Native-action status events carry validated prompts, and browser transport opcode 37 carries bounded results back to the requesting context. The page promise resolves after the user completes the action; rejection uses a browser `DOMException` error name. Client clipboard or sharing failures are shown in the prompt for retry or cancellation.

Right-click opens page actions for plain-text copy, cut and paste; links also offer **Open link in new tab** and **Copy link address**. Eya overrides page context menus; right mouse presses and page `contextmenu` events are not dispatched to Chromium. Dismissing the menu consumes the entire pointer gesture, so it cannot activate the page. The menu adds **Select all text** and **Download image** for image targets. Drag selects remote text, including a final move immediately followed by release; pointer capture loss releases the remote button. Double/triple clicks select a word/paragraph through Chromium. The client mirrors text, link, resize and other standard cursor keywords after explicit `cursor-v1` offer/selection; old peers retain the default cursor. Leaving the page surface or losing the transport restores the default cursor. Cursor reports follow the active page and inspect same-target frames/shadow DOM best effort. Cross-origin out-of-process frames and custom image cursors are not mirrored. Menu actions have icons. Client clipboard permissions still apply. Native context actions currently inspect the top document; links inside cross-origin frames are not inspected.

Internet pages run in headless Chromium on the Eya server. The standalone HTML or SVG client sends input and receives display frames over the Noise-authenticated browser WebSocket. Chromium is started on demand with a private temporary profile and validated SOCKS egress. Install a sandbox-capable Chromium or set `EYA_BROWSER_CHROMIUM` to its executable. To install Chrome for Testing's Stable headless shell, run `python3 scripts/install-chrome-headless-shell.py`; it downloads the matching host build from Google's official feed into `$XDG_CACHE_HOME/eya/chrome-for-testing` (or `~/.cache/eya/chrome-for-testing`). Eya discovers the installed shell there automatically. You can pass an install directory as the script's only argument. The shell runs headless by default, so Eya does not pass Chromium's `--headless=new` flag to it. Keep all archive resources beside its executable. Two Chromium processes can run concurrently. Their stable server session IDs and temporary profiles survive client disconnects until explicit end or detached-session expiry; server restart ends them. Each allows one client attachment, with explicit takeover. See [workspaces.md](workspaces.md) for discovery and workspace behavior. `EYA_BROWSER_GPU_MODE=auto` selects Vulkan when a GPU device is visible, `off` uses software rendering, and `vulkan` forces Vulkan. GPU availability and performance depend on the deployment host.

Browser options contains **Stream resolution** (Native, 1080p, 720p, 540p), **Stream encoding** (JPEG, Efficient lossless, or PNG), **JPEG quality** (95/80/60/40), and **Frame rate limit** (60/30/15/5). Native JPEG quality 80 remains the default. Resolution presets cap encoded dimensions proportionally while retaining the full logical viewport: page layout and input coordinates stay consistent. Settings are saved with the browser panel in its server workspace. The menu shows current viewport dimensions and frame KiB.

**Efficient lossless** uses negotiated 64px changed tiles. Each changed tile chooses lossless replacement or XOR against the last successfully presented canonical frame; broad or poorly compressing changes use independent PNG. It preserves captured text pixels without lowering resolution. Initial keyframes cost more than JPEG, so JPEG80 remains the default for mixed content and motion. A client/server without tile support uses JPEG until support is confirmed. Above 4,194,304 captured pixels the efficient mode uses PNG. References reset on tab/connection changes and dimensions; ordinary PNG fallbacks retain the exact tile reference. Navigation and bounded fallback streaks refresh that reference.

The client decodes each frame before replacing the displayed image. It paces acknowledgments to limit frame rate, retaining one transmitted frame in flight. Chromium's own protocol schema is probed for `sendLastFrame`, which preserves final updates produced while an ACK is pending; older implementations retain at most one extra emitted frame and refresh after input received under backpressure. Image chunks pass through a two-message encrypted writer queue, allowing input dispatch between writes. Display transmissions have a 30-second enqueue deadline and a 15-second ACK watchdog after the final chunk is queued; recovery resets references and requests a fresh frame. Three consecutive tile presentation failures suspend tiles in favor of PNG until an explicit resize/settings request. These limits bound work; they do not eliminate TCP head-of-line delay or bytes already in kernel buffers. Rate limits are ceilings; capture, encoding, transfer and decoding can lower the actual rate. PNG preserves pixels but often costs much more bandwidth for photos. See the [streaming measurements and design rationale](browser-streaming.md).

Resize opcode 3 accepts optional `capabilities:["stream-settings-v1","image-download-v1","cursor-v1","tiles-rgba-v1"]` and `stream:{format:"jpeg"|"png",quality:10..100,maxWidth:320..8192,maxHeight:240..8192,tiles:false|true}`. Unknown optional fields/offers are ignored. A `stream-settings` status selects only offered capabilities and reports settings before frames use the selected encoder. When `cursor-v1` is selected, bounded status events use `{type:"cursor",tabId,cursor}` with a standard CSS cursor keyword; cursor URLs are not downloaded. Frame metadata optionally identifies `format`; absence retains JPEG. Baseline frame tags/chunks/ACK semantics and the 16 MiB encoded-frame limit are unchanged. New tile frames use separate tags 147/148 only after `tiles-rgba-v1` selection and `stream.tiles:true` with PNG capture. Tile presentation uses opcode 39; baseline image ACK opcode 5 cannot commit a tile reference. See the [streaming improvement protocol and results](browser-streaming-improvements.md). Old clients keep JPEG80; new clients keep baseline JPEG with old servers and display an unsupported-controls notice. Encoding selections reset on detach/takeover; stale frames in another encoding are discarded and acknowledged.

Image download opcode 38 is accepted only after explicit `image-download-v1` selection. It carries the active `tabId` and finite, in-viewport `x/y` coordinates; the server locates the image rather than accepting a client URL. HTTP(S) images are read by Chromium through its existing validated SOCKS egress, including redirects and cookies, then streamed over existing bounded download messages. Same-page blob images and inline image data (up to 2 MiB) are supported. Local-file URLs and other protocols remain rejected. Downloads keep the 64 MiB transfer limit, bounded CDP reads, deadline and private temporary-file cleanup used by PDF downloads. Cross-origin-frame inspection remains unsupported.

The browser endpoint is part of the main Eya server; there is no separate browser service to start. The server process must run as a non-root user on a host that supports Chromium's sandbox, with Chromium and its system dependencies installed. For the Chrome for Testing Headless Shell on Ubuntu 24.04, install its runtime dependencies with `sudo apt-get install ca-certificates fonts-liberation libasound2t64 libatk-bridge2.0-0t64 libatk1.0-0t64 libatspi2.0-0t64 libcairo2 libcups2t64 libcurl4t64 libdbus-1-3 libexpat1 libgbm1 libglib2.0-0 libgtk-3-0t64 libnspr4 libnss3 libpango-1.0-0 libudev1 libvulkan1 libx11-6 libxcb1 libxcomposite1 libxdamage1 libxext6 libxfixes3 libxkbcommon0 libxrandr2`. On other distributions, install the corresponding packages listed in the shell archive's `deb.deps` or `rpm.deps`. You can override automatic discovery with `EYA_BROWSER_CHROMIUM`. The current Docker image does not include Chromium and runs Eya as root, so it does not support the server browser without additional deployment work. After updating Eya, rebuild the client and server and restart the server to use the updated embedded client and backend.

**Proxy browser → Browser options → Local HTML** opens an HTML file under Eya's file root. It is no longer part of the server Chromium panel. Relative links to other HTML files and relative presentation assets are read through the authenticated file transport. Scripts are disabled; dynamic applications and script-based search do not work in this viewer.

The Chromium panel keeps the simplified controls. Back and Forward use the active Chromium tab’s navigation history. Proxy browser provides Find, privacy, bookmarks, history, page zoom, downloads, and Local HTML. The proxy uses the same sandbox in generated HTML, SVG, compressed HTML, compressed SVG, and data URL clients and in hosted HTML and SVG. If a data URL cannot connect to a local address under the browser’s network policy, use **Open server client** in the connection dialog.

Interactive proxy pages execute JavaScript in an opaque-origin iframe with exactly `sandbox="allow-scripts"`. When the client lacks the Navigation API, the proxy opens pages in reader mode. Reader mode preserves text selection, proxied styles and images, ordinary navigation, Find, and GET forms. It disables site scripts, imported scripts, DevTools evaluation, and POST forms. Use the Browser panel for sites that require those features. Some interactive proxy page requests can use the client device’s network. See the [API inventory](browser-proxy-apis.md) and [compatibility corpus](browser-proxy-compatibility.md).

The proxy opens a fresh authenticated channel automatically when the WebSocket reports a connection failure. It backs off between attempts, up to ten seconds. New body-free GET/HEAD requests may wait for the current attempt. An open page stays in place, and interrupted requests and upstream sockets are never replayed. A submission interrupted after send reports unknown completion. Disconnecting explicitly pauses recovery until the workspace reconnects. Closing a panel cancels retries and connection waits.

The proxy collects bounded DOM snapshots only while inspecting the active page in the Elements drawer. Closing DevTools or switching drawers stops DOM inspection and avoids rendering the hidden DevTools UI.

Proxy workspaces save up to 24 GET tab destinations, the active tab, and page zoom in versioned bounded metadata. Only the active tab loads on restoration. Other tabs load when selected. Each URL is limited to 4096 characters and the snapshot to 7000 bytes. Unsafe, over-budget, loading, failed, and POST destinations save as blank tabs. Cookies, virtual storage, imported scripts and filters, and page execution state belong to the panel lifetime. The local viewer requires explicit opening. Valid response credit arriving after completion or cancellation is ignored. Malformed or oversized credits and overflowing active queues are rejected.

Proxy compatibility in 2.6.0 adds bounded gzip/deflate decoding, parser-ordered initial scripts, synchronous interception of common dynamic resource insertion, upstream script identities and virtual URL reads, shared CSS token rewriting, and bounded on-demand same-origin page module graphs. These mechanisms retain the opaque iframe and its restrictive CSP; they do not grant upstream origin privileges or native persistent storage. [Proxy delivery plan](browser-proxy-roadmap.md) · [Documentation workflows](browser-proxy-26-sites.md)

Server browser resource usage depends on the page. Optional hard limits require a writable delegated cgroup v2 subtree in `EYA_BROWSER_CGROUP_ROOT`; `EYA_BROWSER_CGROUP_MEMORY_MB`, `EYA_BROWSER_CGROUP_CPU_PERCENT`, and `EYA_BROWSER_CGROUP_PIDS` tune the limits. Without a delegated subtree, Chromium's renderer and JavaScript heap settings are best-effort limits, not a hard aggregate cap. A systemd service can alternatively set aggregate `MemoryHigh=`, `MemoryMax=`, `CPUQuota=`, and `TasksMax=` for Eya and its children.

The browser WebSocket is authenticated with the Eya key. Destination validation, public-address checks, DNS pinning, and redirected-request validation apply on server egress. The client-side viewer should not be treated as a general sandbox for executing local HTML scripts.

For the current inventory of native browser APIs, existing bridges, and proposed compatibility work, see [browser-api-roadmap.md](browser-api-roadmap.md).

## Shared settings and shortcuts

Settings → Browser configures streaming and privacy defaults and updates open panels. Panel options save back to workspace preferences. Navbar → Keyboard shortcuts provides searchable Browser and Global bindings. Basic-mode pages receive bounded binding updates over their private MessagePort; the host revalidates the action, active tab and current binding. Only trusted keyboard input can relay actions, and native event/channel methods are captured before page scripts run. Full-browser input uses the same configured actions before remote keyboard forwarding.
